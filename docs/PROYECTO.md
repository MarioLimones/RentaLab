# RentaLab: contrato, decisiones y progreso

Este documento es la referencia para continuar el proyecto. Antes de cada fase se debe leer y después actualizar con las decisiones, cambios y comprobaciones ejecutadas. El objetivo es estudiar el código y presentar un screencast técnico a LeanMind con una aplicación original y datos ficticios.

## Contrato del producto

- **Alcance vigente desde fase A (15/10/2026):** se sustituye el operador único por visitantes, clientes y administradores dentro del mismo React y FastAPI. Visitantes consultan catálogo, características y disponibilidad por fechas; clientes pueden crear, consultar y cancelar sus reservas, consultar perfil e informar de problemas vinculados a ellas; administradores gestionan equipos, todas las reservas, incidencias, importaciones y su panel. Las fases 1–8 que siguen son el registro histórico del alcance anterior.
- La **fase A: base de usuarios y permisos**, descrita en [ACCESO.md](ACCESO.md), incluye registro/acceso/sesión/cierre, administrador explícito, ownership nullable y protección de los recursos existentes. La **fase B** añade la [API de catálogo público](CATALOGO_PUBLICO.md) bajo `/api/public`, con presentación separada de gestión y disponibilidad sin datos privados. La **fase C** incorpora las [operaciones propias de reservas y avisos](OPERACIONES_CLIENTE.md) bajo `/api/me`. La **fase D** implementa el [portal React](PORTAL_CLIENTE.md) con catálogo, acceso y operaciones propias; conserva el panel bajo `/admin`. La **fase E** completa el [panel y su conexión con el portal](ADMINISTRACION.md): edición pública de equipos, reservas globales con propietario/origen, gestión de avisos y respuesta pública, usando permisos y reglas comunes.
- Una unidad de equipo representa un objeto físico y tiene un código único.
- Las reservas ocupan días completos con inicio incluido y fin excluido: del 10 al 12 ocupa los días 10 y 11; otra reserva puede comenzar el 12.
- Los pedidos importados crearán reservas.
- Las incidencias bloqueantes impedirán nuevas reservas de la unidad afectada.
- Cancelar una reserva o resolver una incidencia conservará su historial.
- Las reglas de negocio y la validación definitiva pertenecen a Python. React consume la API.
- No se publican ni contratan servicios externos como parte del desarrollo de estas fases.

La fase 1 dejó documentadas las reglas de reservas, pedidos e incidencias. La fase 2 implementa las reservas, la fase 3 las conecta con incidencias, la fase 4 importa pedidos CSV como solicitudes de reserva individuales, la fase 5 incorpora el panel React conectado, la fase 6 protege el acceso, la fase 7 prepara el empaquetado persistente y la fase 8 revisa el conjunto y prepara su explicación.

## Decisiones de la fase 1

1. El código de cada unidad se normaliza con `strip()` y mayúsculas antes de persistirlo. La comprobación de duplicados se combina con una restricción de SQLite, de modo que el almacenamiento también exige unicidad.
2. Las operaciones del catálogo son crear, listar, consultar, reemplazar los datos editables con `PUT` y editar parcialmente con `PATCH`. `active` se modifica mediante la misma edición parcial; desactivar no borra la unidad. El identificador lo asigna el servidor.
3. Un duplicado devuelve HTTP 409; una unidad inexistente, 404; los datos inválidos, 422. La documentación OpenAPI vive bajo `/api` junto a los recursos del producto.
4. La configuración del backend se obtiene del entorno o de `.env` en la raíz con prefijo `RENTALAB_`. `RENTALAB_ENVIRONMENT` acepta `development`, `test` o `production`. Por defecto se utiliza `data/rentalab.db` con una ruta absoluta calculada para que no dependa del directorio de lanzamiento. `.env` y bases locales no se versionan.
5. El esquema cambia únicamente con Alembic. Iniciar FastAPI no reinicializa ni borra datos. El comando explícito `python -m rentalab.seed` carga ejemplos ficticios de forma repetible sin duplicados.
6. En desarrollo, Vite reenvía `/api` y `/health` a FastAPI. En producción FastAPI sirve `frontend/dist` y la API bajo el mismo origen. No se necesita CORS para esos flujos y no se exponen secretos al frontend.
7. `requirements.lock` fija dependencias de ejecución y `requirements-dev.lock` añade las herramientas de desarrollo con hashes. `package-lock.json` fija el árbol npm y las instalaciones reproducibles usan `npm ci`.
8. Docker compila primero React y ejecuta Python con usuario sin privilegios. Usa `/data` como volumen SQLite. El arranque del contenedor aplica migraciones pendientes; la carga ficticia sigue siendo explícita.
9. El entorno virtual de desarrollo queda fuera del control de versiones. En Windows se llama directamente a `python.exe` y `npm.cmd`, sin requerir activar scripts PowerShell.
10. Los códigos normalizados admiten 1–40 caracteres ASCII: letras, números, guion y guion bajo; el primero debe ser letra o número. Nombre y categoría requieren contenido y tienen límites de 120 y 80 caracteres; descripción, 2000. Los textos se recortan y `active` requiere un booleano real. Se rechazan campos desconocidos. Son decisiones rutinarias de esta demostración, no requisitos de un negocio real.
11. `description` vale `""` y `active` vale `true` cuando se omiten en creación o reemplazo. En `PATCH` los campos omitidos se conservan, no se aceptan nulos ni un objeto vacío. OpenAPI describe estos límites y los errores HTTP. Listar incluye unidades inactivas y permite filtrar por `active`, ordenando por código.
12. La migración `0001_equipment` crea el catálogo. Tras aplicarla se descubrió que SQLite podía admitir NUL en una escritura SQL directa. Se conservó la migración original y se añadió `0002_equipment_code_no_nul`, con una restricción adicional mediante la reconstrucción controlada de Alembic para SQLite. Los identificadores y las cuatro unidades locales se conservaron.
13. `GET /health` comprueba que el proceso HTTP responde; no es una comprobación de disponibilidad del esquema SQLite. Las migraciones deben aplicarse antes de usar el catálogo. La aplicación nunca crea tablas mediante `create_all`.

## Cómo recorrer el código

Una petición entra en `backend/rentalab/equipment/routes.py`. FastAPI usa los esquemas de `schemas.py` para validar y normalizar el JSON. `service.py` decide si la unidad existe y si su código está disponible, sin depender de objetos HTTP. `repository.py` consulta y guarda con una sesión SQLAlchemy; `models.py` describe las restricciones persistentes. Si dos escrituras compiten por el mismo código, la restricción única de SQLite es la defensa definitiva y el servicio traduce ese conflicto a un error de dominio; FastAPI lo presenta como HTTP 409.

En React, `src/api/client.ts` centraliza `fetch`, los errores y la comprobación de la estructura de las respuestas; los tipos están en `src/types/api.ts`, reexportados por el cliente para conservar sus consumidores. Esa comprobación protege al consumidor; no reemplaza la validación definitiva de Python. `App.tsx` define navegación y rutas; las páginas consumen la API mediante hooks locales. El componente de conexión conserva la consulta de salud y su reintento. [INTERFAZ.md](INTERFAZ.md) permite recorrer el código y los flujos.

## Decisiones de la fase 2

1. El módulo `rentalab/reservations` mantiene esquemas, servicio, repositorio, modelo y rutas separados. `rentalab/http.py` comparte la sesión por petición y el esquema de errores con equipos. La pantalla React no cambia.
2. El alta sólo acepta equipo, cliente, fechas y referencia opcional. El servidor asigna `confirmed`; la única transición disponible es a `cancelled`, conservando todos los demás datos. No hay borrado ni reutilización de referencias canceladas.
3. Disponibilidad y creación llaman al mismo método del servicio. Sólo bloquean las reservas confirmadas del mismo equipo que cumplen `existing.start_date < requested.end_date AND existing.end_date > requested.start_date`. La disponibilidad es informativa y se vuelve a comprobar al crear; no existe una columna `available`.
4. Crear y cancelar usan una sesión nueva y `Session.begin()` con `BEGIN IMMEDIATE` antes de leer. La comprobación y la escritura se serializan entre conexiones y procesos. Se conserva el modo heredado de sqlite3/Python 3.12; no se introduce un listener global de `BEGIN` que pueda anidar transacciones. Las futuras escrituras de reservas deben respetar esta unidad de trabajo.
5. La espera SQLite es configurable mediante `RENTALAB_SQLITE_BUSY_TIMEOUT_MS` (5000 por defecto, 0–60000). Se reconocen los códigos primarios `SQLITE_BUSY`/`SQLITE_LOCKED`, incluidas sus variantes extendidas. Al agotarse el bloqueo se revierte la transacción y se responde 409 con `Retry-After: 1`. No hay reintento automático de altas ni se convierten otros errores de persistencia en conflictos falsos.
6. Los filtros combinables son equipo, estado y un intervalo completo. El intervalo selecciona reservas que lo solapan; no sólo las que empiezan dentro. Se devuelven también canceladas si no se filtra por estado. El orden es fecha de inicio e identificador.
7. Las fechas HTTP exigen ISO exacto, sin horas ni números de época. Nombre y referencia tienen límite de 120 caracteres y rechazan NUL; los identificadores se limitan al entero positivo SQLite de 64 bits. Las referencias se recortan, distinguen mayúsculas/minúsculas y permiten múltiples `null`. No se impone fecha futura.
8. Se añade `email-validator` 2.3.0 y su dependencia fijada con hashes para validar sintaxis y normalizar correos sin DNS ni mensajes; se admiten direcciones ficticias `.test`. Los locks conservan el resto del entorno.
9. `0003_reservations` añade tabla, clave foránea, restricciones de rango y estado, referencia única e índice por equipo/estado/fechas. Las dos migraciones anteriores y sus datos se conservan. No se cargan reservas al iniciar ni al ejecutar el seed de equipos.
10. El cliente API incorpora tipos, filtros, creación, consulta, cancelación y disponibilidad mediante `/api` relativo. Sólo comprueba la estructura de respuestas; las reglas de negocio permanecen en Python. La UI de reservas sigue reservada para la fase 5.

## Decisiones de la fase 3

1. `rentalab/incidents` separa modelo, esquemas, repositorio, servicio y HTTP, siguiendo la estructura existente. Una incidencia pertenece a un equipo que debe existir; puede estar inactivo para registrar problemas de material fuera de servicio.
2. Al crear se asignan `open` y resolución vacía. Descripción vacía, prioridad `medium` y `blocking=false` son los valores por defecto. El título requiere 1–160 caracteres y los textos descriptivos hasta 2000, recortados y sin NUL. No se admiten campos desconocidos ni tipos booleanos coercionados en las altas.

## Reservas multiusuario: decisiones actuales (15/10/2026)

1. Se conserva el stack y la separación entre portal y administración. La autenticación real y el ownership de servidor ya estaban implementados; no se añade otra sesión ni se confía en una identidad enviada desde React. `rentalab.demo` crea explícitamente un administrador y cinco clientes con contraseñas ficticias distintas, cuatro unidades y seis reservas relativas al día Madrid o a `--base-date`. Elena queda sin reservas. [RESERVAS_MULTIUSUARIO.md](RESERVAS_MULTIUSUARIO.md) documenta credenciales, comando, fechas y recorrido.
2. La carga es insert-only: correos/códigos/referencias estables, sin reset ni cambio de contraseñas, roles, fechas o estados existentes. Repetir con otra fecha conserva los históricos; para una cohorte futura nueva se usa otra SQLite local migrada. Los conflictos se informan sin corregir datos existentes. Se rechaza `production` antes de abrir la base y no se invoca desde arranque/migraciones. La reserva cancelada se crea con su estado inicial dentro de la transacción común, sin una confirmación intermedia que pudiera quedar ocupando fechas por interrupción.
3. `GET /api/public/equipment/{id}/calendar` publica sólo fechas confirmadas, recortadas y agrupadas dentro de un intervalo máximo de 366 días, más `can_book` genérico. Nunca publica nombres, correos, referencias, identificadores de reservas ni detalles de incidencias. Las canceladas no bloquean; una incidencia bloqueante impide nuevas reservas; un equipo inactivo devuelve 404 público y el alta se vuelve a comprobar en servidor.
4. React muestra un calendario mensual accesible con texto de ocupado/libre, navegación por meses y explicación de fin excluido. Refresca calendario y rango tras crear o recibir conflicto; al cancelar consulta de nuevo el rango desde el detalle y vuelve a cargar el calendario al entrar en la ficha. Un 409 conserva las fechas, explica el cambio y permite elegir otro periodo/equipo. No hay éxito anticipado ni comunicación push entre ventanas. Confirmación y cancelación llevan una guarda inmediata contra doble clic.
5. La atomicidad existente era correcta y se conserva: `Session.begin()` más `BEGIN IMMEDIATE` antes de leer las reglas, compartida por portal, administrador e importación. SQLite serializa escritores de conexiones/procesos distintos; el segundo lee el commit del primero antes de decidir. La condición de solapamiento incluye la unidad física y usa `[inicio, fin)`, permitiendo adyacencias y unidades distintas aunque sean el mismo modelo. No se añade un bloqueo en memoria ni un listener global que anide transacciones.
6. Se corrige la ambigüedad de errores de espera: `SQLITE_BUSY`/`SQLITE_LOCKED` agotado devuelve ahora **503 con `Retry-After: 1`**, también si ocurre al consultar sesión, y hace rollback incluso ante fallo de commit. **409** significa conflicto de negocio, sin cabecera de reintento. La espera tiene un límite configurable de 5000 ms por defecto; no hay bucle ni reenvío automático de altas. Un reintento explícito vuelve a ejecutar todas las comprobaciones. CSV conserva su informe por fila HTTP 200, con rechazo y mensaje de reintento para la fila bloqueada.
